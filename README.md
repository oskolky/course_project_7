# Log Analyzer

Гибридная интеллектуальная система для выявления, классификации и объяснения ошибок веб-сервера по журналам событий. Логико-символьный контур (версионируемая база знаний правил) и нейробионический контур (Isolation Forest) работают независимо, а арбитраж согласовывает их результаты и формирует инциденты с доказательствами.

Реализован на Python в соответствии с проектной архитектурой курсовой работы.

## Возможности

- загрузка NGINX/Apache access log, error log, JSON Lines и структурированных записей API;
- нормализация к единой схеме события с сохранением исходной строки;
- диагностика повреждённых записей с понятным описанием причины, без остановки обработки;
- шаблонизация сообщений методом на основе наибольшей общей подпоследовательности;
- корреляция по trace ID и request ID, ограниченная эвристика при их отсутствии;
- построение временных окон и векторов признаков;
- версионируемые YAML-правила трёх областей действия (событие, группа, окно) с проверкой условий;
- Isolation Forest с перечнем отклонившихся признаков для аномального окна;
- арбитраж: известный сбой, известный сбой с подтверждением моделью, необъяснённое отклонение, конфликт правил;
- инциденты с доказательствами, затронутыми запросами и рекомендацией; ручная проверка конфликтов;
- пошаговый протокол запуска и решение по каждому окну;
- поиск записей по времени, источнику, коду ответа, уровню серьёзности, идентификатору запроса, шаблону и тексту;
- сводка с распределением инцидентов по значимости и типам, уведомления о границах применимости результата;
- сокрытие секретов при сохранении и при выводе, маскирование почты и последнего октета IPv4 в API;
- REST API, асинхронные запуски анализа, веб-интерфейс;
- SQLite по умолчанию и PostgreSQL через `DATABASE_URL`; схема прежних версий дополняется при запуске.

## Запуск

Требуется Python 3.12 или новее.

```bash
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt      # Linux и macOS: .venv/bin/pip
.venv/Scripts/python main.py                       # Linux и macOS: .venv/bin/python
```

Откройте `http://localhost:3000`. Документация API доступна по адресу `http://localhost:3000/docs`.

Для PostgreSQL:

```bash
export DATABASE_URL='postgresql+psycopg://user:password@localhost:5432/log_analyzer'
python main.py
```

Для Docker:

```bash
docker build -t log-analyzer .
docker run --rm -p 3000:3000 -v log-analyzer-data:/app/data log-analyzer
```

## Демонстрация

Кнопка «Запустить демо» загружает связанные access/application/error logs и запускает полный анализ. В демонстрационном наборе есть рост ответов 401, массовые 404 статических ресурсов, тайм-ауты upstream с ответами 504 и одна повреждённая JSON-строка.

Кнопка «Анализировать по правилам» запускает тот же набор без модели — так сравниваются чисто символьный и гибридный варианты.

Более крупный сценарий с пятью заложенными аномалиями собирает генератор `samples/generated/generate_logs.py` (описание — в `samples/generated/README.md`).

## Основные API-ресурсы

- `POST /api/datasets` — multipart-загрузка файлов; `POST /api/datasets/json` — массив структурированных записей;
- `DELETE /api/datasets/{dataset_id}` — удаление набора со всеми производными данными;
- `POST /api/maintenance/purge` — очистка реестра журналов одной транзакцией (правила и модели сохраняются);
- `POST /api/analysis` — запуск анализа набора: с моделью (`model_id`) или только по правилам;
- `GET /api/runs/{run_id}` — состояние запуска; `GET /api/runs/{run_id}/protocol` — шаги обработки и решение по каждому окну;
- `GET /api/events`, `GET /api/events/count` — поиск нормализованных событий: `time_from`, `time_to`, `source_type`, `service`, `route`, `status`, `severity`, `request_id`, `template_id`, `q`, постранично через `limit` и `offset`;
- `GET /api/templates` — шаблоны сообщений с числом вхождений; `GET /api/groups`, `GET /api/groups/{id}` — группы связанных событий с качеством связи;
- `GET /api/incidents` — реестр с фильтрами; `GET /api/incidents/{incident_id}` — карточка с доказательствами; `PATCH /api/incidents/{incident_id}/review` — отметка ручной проверки;
- `GET /api/rules`, `POST /api/rules` — версии YAML-правил; условие, не относящееся к области действия правила, и дубль уже опубликованного правила отклоняются;
- `GET /api/models`, `POST /api/models/train` — реестр и обучение моделей; в параметрах модели возвращаются признаки, которые в обучающем периоде не менялись (`constant_features`);
- `GET /api/overview` — временные ряды, распределение инцидентов по значимости и типам, уведомления о границах результата;
- `POST /api/demo` — демонстрационный сценарий.

## Поведение, которое стоит знать

- Повторный анализ того же набора в той же конфигурации (та же модель, тот же состав правил) возвращает тот же идентификатор запуска и те же идентификаторы инцидентов; отметки ручной проверки сохраняются.
- Окно с числом запросов меньше `MIN_WINDOW_REQUESTS` (по умолчанию 3) имеет статус `insufficient_data`: модель его не оценивает. Сработавшее в таком окне правило по умолчанию всё равно создаёт инцидент, но с предупреждением об отсутствии статистического подтверждения; `RULES_IN_INSUFFICIENT_WINDOWS=false` запрещает и такие инциденты.
- Инцидент относится к сервису записей с приметой ошибки (например, приложения, сообщившего о причине), а не к самому частому сервису окна.
- Правило с областью `event` проверяется на отдельной записи, `group` — на связанных событиях одного запроса, `window` — на окне целиком. Необязательные поля правила `title` и `recommendation_text` выводятся в интерфейсе вместо служебных идентификаторов.
- В YAML-правилах последняя версия каждого правила считается действующей; опубликованные версии не изменяются. Если сохранённая версия разошлась с файлом `configs/rules.yaml`, сервер сохраняет её и записывает предупреждение в журнал.

## Проверка

```bash
python -m pytest
python tools/test_report.py                                  # отчёт о тестировании в docs/test-report.md
python tools/test_report.py --benchmark http://127.0.0.1:3000  # то же с замерами на отдельном экземпляре
```

Тесты используют отдельную временную SQLite-базу и не изменяют рабочие данные. Каждый тест относится к одной из групп — типичные, граничные или отрицательные сценарии — и описывает задействованные компоненты и ожидаемый результат. Покрыты загрузка и обработка записей, защита данных, база знаний, модель, арбитраж, REST API и двенадцать сквозных сценариев.

`--benchmark` загружает и удаляет наборы данных и добавляет в базу правил неиспользуемые правила, поэтому выполняется только на отдельном экземпляре с пустым реестром.

## Структура

```text
log_analyzer/
  api/           REST API и фоновые запуски
  ingestion/     адаптеры входных форматов
  processing/    нормализация, маскирование, шаблоны, группы и окна
  features/      схема и векторы признаков
  knowledge/     YAML-правила и контур правил
  models/        Isolation Forest и артефакты моделей
  arbitration/   таблица решений, построение инцидентов и протокол
  storage/       ORM, миграция схемы и сериализация
  services/      сквозной конвейер и обслуживание
  web/           загрузка журналов, инциденты, шаблоны, протокол и поиск
configs/         версионируемая база знаний
samples/         фиксированные журналы и генератор синтетических наборов
tests/           тесты трёх групп и сквозные сценарии
tools/           формирование отчёта о тестировании
docs/            отчёт о тестировании
```

Статистическая оценка не трактуется как предметная причина. Порог аномалии равен квантилю оценок обучающей выборки, поэтому часть спокойных окон получает вид `unknown_anomaly` и остаётся кандидатом для осмотра. При недоступности модели контур правил продолжает работу, а ограничение фиксируется в уведомлениях запуска. API не требует аутентификации и предназначен для запуска в изолированном окружении.
